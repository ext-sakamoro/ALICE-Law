Test `Requirers`; a mutant that lets a registry copy pass is red
- G11 (c), a rollout no longer turns Law main red. `scripts/shared_files_check.py --live` counts a copy that a main holds without the table listing it, when it has its row's bytes (or a pending row's variant), as an unlisted holder: it prints the repository, path, sha256 and the date the copy appeared, plus the oldest such date. A copy with other bytes, and an unregistered file that discovery finds, stay findings. `scripts/gen_shared_files.py --check` likewise reports a row that only gained such holders. With `--strict` (both scripts) an unlisted holder is a finding; a pending row's moving variants stay reported, since they move during its rollout by definition. `scripts/preflight.sh` and the publish gate (`release_train.py publish-gate`, which now runs `shared_files_check --live --strict`) use it, so the table cannot stay stale into a release. A pending row's target bytes are accepted in a crate's tree and on a main before a regeneration records them as a variant (a crate that already took the target is not drift). Tests 37 + 18 and the publish-gate cases. Mutants, each red: a 1-byte different copy, an unknown shared file, the note counter at 0, strict ignoring unlisted holders, the generator putting back a different-bytes row, strict --check ignoring them, and the publish gate skipping the check
- G11 (c), files shared byte for byte across the crates: `conformance/shared-files.toml` (105 files in 16 repositories: 93 uniform, 11 pending, and 1 per-repository path whose holders are all exempted). A change that adds or settles a row regenerates the table and the count lock in the same commit, immediately before it lands, generated by `scripts/gen_shared_files.py` from the shared-file rows, a discovery pass and each listed repository's main. Each row lists every table repository that has the path on main. When all copies agree, the row records their SHA-256 and a source commit. When they differ, or a row is moving to new bytes, the row is `pending`: the variants found, the `target` bytes and their `owner`, the date it became pending and what ends it. It pins no bytes, and it becomes uniform only when every copy has its target. `scripts/shared_files_check.py` has four modes. `--table` checks the schema, with `--base-table` refusing a rise in pending rows. `--fetch` checks that each uniform source commit is on main with the entry's bytes. `--live` checks every listed main (`--expect-copies` locks the number of copies of uniform rows, which moves only with the table; a pending row's copies come and go as its rollout lands). Pending rows are listed there, and a pending row is red after 21 days. Its discovery pass is red for a file under `scripts/`, `tools/` or `.github/workflows/` that is byte-identical in two table repositories with no entry (a shared copy elsewhere, under `tests/` or `src/`, is checked only once a row names it), and for a copy on a main that its entry neither lists nor exempts. `--repo DIR --name ALICE-X` checks a crate's tree: a uniform copy must equal its entry, a pending copy must be one of its row's variants (it is listed, so the crate's cell is not a pass), and an unlisted copy at a table path is red. Every mode prints `compared: files N, repos M, copies K, pending P`. A finding exits 1; nothing compared exits 2. The blobs are fetched in one request per repository. Tests: `scripts/test_shared_files_check.py` (33) and `scripts/test_gen_shared_files.py` (11), against local bare repositories. They run in `dependency-consistency.yml` and `scripts/preflight.sh`, offline: the schema, the ratchet against main's table, and this repository's own copies. This repository's `public-text.yml` is exempt because it runs the checker in place. `conformance-live.yml` gets a `shared-files` job: `--fetch`, `--live --expect-copies 766`, and the generator's `--check`, which reports a pending row's moving variants without failing. Documented in docs/CONFORMANCE.md (G11)

- `semver-config-drift` also checks that each run of `scripts/semver_gate.py` can fail its workflow and is reached by a push to main that changes the gate. The gate is the whole of its step's `run`: one simple command after comments and blank lines, with only redirections after it and only assignments and the interpreter before it, so a list, negation, condition, group, function, subshell or `set +e` around it is refused (errexit does not stop in all of them), as is a run that only expands the gate from an env value; `continue-on-error` on the step or the job, a step shell other than bash / sh, an `if:` other than the push / pull_request event conditions, a workflow that does not run on push to main or whose `on.push.paths` leaves out the gate or its config, and `paths-ignore` on push. A job gated by `needs.changes.outputs.run == 'true'` is accepted only with an `if: always()` gate job that needs both the changes job and it, runs `changed_paths.py gate` without `||` and has no other condition or `continue-on-error`, and with a decide step that reads one literal `--patterns-file` listing the gate and its config (and equal to `on.pull_request.paths`)
- `scripts/release_train.py semver-config-drift`: anchored on each roster repository's tracked files.
